## Executive Summary

This document provides comprehensive security guardrails for Microsoft Power Platform deployment within Canadian Federal Government departments and agencies, financial institutions, and regulated organizations to meet Protected B, Medium Integrity, Medium Availability (PBMM) requirements as defined by the Canadian Centre for Cyber Security (CCCS) and aligned with ITSG-33 standards.

**Key Updates in Version 2.1:**

- **Security Score Integration:** Leverage the Power Platform Security Score to measure and improve your organization's security posture
- **Customer-Managed Keys (CMK):** Now classified as OPTIONAL for enhanced data protection control
- **Power Platform Pipelines:** Native ALM capabilities for governed solution deployment
- **CoE Starter Kit Integration:** Reference implementation for governance, monitoring, and adoption
- **Managed Environments Evolution:** Enhanced capabilities across Managed Governance, Managed Security, and Managed Operations

These guardrails are designed to ensure compliance with:

- CCCS Medium Cloud Profile Recommendations
- Government of Canada Security Control Profile for Cloud-based GC Services
- ITSG-33 Annex 4A - Profile 1 (PBMM)
- Privacy Act and Access to Information Act requirements
- CISA Microsoft Power Platform Secure Configuration Baseline

## NEW: Power Platform Security Score

### Overview

The Power Platform Security Score provides a centralized measurement of your organizational security position. This score is calculated based on security features enabled across your environments and helps identify areas for improvement.

**Access:** Power Platform Admin Center > Security > Overview

### Security Score Categories

The security score is displayed on a qualitative scale:

| Score Range | Assessment | Description |
|-------------|------------|-------------|
| 0-50 | Low | Significant security improvements needed |
| 51-80 | Medium | Good foundation with room for enhancement |
| 81-100 | High | Strong security posture |

### Score Calculation

The security score is calculated using: `(Your Score ÷ Total Possible Score) × 100`

Each security feature is assigned points based on scope (tenant or environment) and the number of resources affected. Features that contribute to the score include:

| Feature | Scope | Impact |
|---------|-------|--------|
| IP Firewall | Environment | Points per environment enabled |
| Tenant Isolation | Tenant | Points when enabled |
| Environment Security Group | Environment | Points per environment configured |
| IP Address-Based Cookie Binding | Environment | Points per environment enabled |
| Data Policies (DLP) | Tenant/Environment | Points when tenant-level policy exists |
| Customer Lockbox | Tenant | Points when enabled (Managed Environments) |
| Auditing | Environment | Points per environment enabled |
| Sharing Limits | Environment | Points per environment configured |
| Guest Access Restrictions | Environment | Points per environment configured |

### Recommendations Engine

The Security Score generates actionable recommendations based on best practices:

| Condition | Recommendation Triggered |
|-----------|-------------------------|
| >10 administrators per environment | Reduce administrator privileges |
| Auditing disabled | Enable auditing |
| No tenant-level DLP policy | Create tenant data policy |
| No environment security group | Configure security group |
| Tenant isolation off | Enable tenant isolation |
| No IP firewall | Configure IP firewall |
| No sharing limits | Implement sharing controls |

### Implementation Requirements (MANDATORY)

**Prerequisites:**

1. Enable tenant-wide analytics (Power Platform Admin Center > Manage > Tenant Settings > Analytics)
2. Wait up to 24 hours for initial score calculation
3. Assign Power Platform Administrator or Dynamics 365 Administrator role

**Target Security Score:** Organizations should aim for a **Medium (51-80)** score minimum, with a goal of achieving **High (81-100)** for production environments handling Protected B data.

## 1. Tenant-Level Security Configuration

### 1.1 Environment Provisioning Controls (MANDATORY)

**Requirement:** Restrict environment creation to authorized administrators only.

**Configuration:**

- **Production Environments:** Only specific admins
- **Trial Environments:** Only specific admins  
- **Developer Environments:** Only specific admins

**Authorized Roles:**

- Global Administrator
- Power Platform Administrator
- Dynamics 365 Administrator

**Rationale:** Prevents environment sprawl and ensures proper data sovereignty controls. This aligns with CISA baseline MS.POWERPLATFORM.1.1v1.

**Verification:** Navigate to Power Platform Admin Center > Settings > Tenant Settings > Environment Provisioning

**Security Score Impact:** This configuration contributes to overall governance posture.

### 1.2 Cross-Tenant Inbound/Outbound Restrictions (MANDATORY)

**Requirement:** Block all cross-tenant data sharing and external tenant access.

**Configuration:**

- Disable cross-tenant inbound connections
- Disable cross-tenant outbound connections
- Block external user sharing
- Restrict guest user access

**Implementation:** Power Platform Admin Center > Settings > Tenant Settings > Cross-tenant access

**Security Score Impact:** Tenant isolation contributes points when enabled across all environments.

### 1.3 Data Loss Prevention (DLP) Policies (MANDATORY)

**Requirement:** Implement comprehensive DLP policies at both tenant and environment levels.

**Security Score Note:** The recommendation for data policies is triggered when there is no tenant-level policy defined. Environment-scoped policies alone do not satisfy the security assessment requirement.

#### Tenant-Wide DLP Policy

**Scope:** All environments  
**Purpose:** Block high-risk connectors organization-wide

**Blocked Connectors (Minimum):**

- Social media platforms (Twitter, Facebook, Instagram, LinkedIn)
- Public file sharing (Dropbox, Google Drive personal, Box personal)
- Personal cloud storage services
- Anonymous survey tools
- Public forums and wikis
- Cryptocurrency services
- Gaming platforms
- Dating applications

**Business Category Connectors:**

- Microsoft 365 (SharePoint, Teams, Outlook, OneDrive for Business)
- Microsoft Dataverse
- Azure services (SQL Database, Key Vault, etc.)
- Approved government systems

**Non-Business Category:**

- Internal tools and approved third-party services
- Testing and development connectors

#### Environment-Specific DLP Policies

**Production Environments:**

- More restrictive than tenant policy
- Only pre-approved business connectors
- Audit all connector usage
- Enable connector action-level controls

**Development/Test Environments:**

- Slightly less restrictive for testing
- Still block high-risk public connectors
- Enable additional logging

**Advanced DLP Capabilities (Managed Environments):**

- Block any connector including standard Microsoft connectors (SharePoint, Approvals)
- Configure connector action-level controls
- Endpoint filtering for HTTP connectors

### 1.4 Maker Portal Settings (MANDATORY)

**Configuration:**

- Disable maker welcome content (or customize for government use)
- Disable community content sharing
- Restrict template gallery access
- Disable sample app installation
- Enable admin notification for new apps

## 2. Environment-Level Security Configuration

### 2.1 Security Groups (MANDATORY)

**Requirement:** All environments must be associated with Microsoft Entra security groups.

**Implementation:**

- Create dedicated security groups for each environment
- Implement least privilege access
- Regular access reviews (quarterly minimum)
- No direct user assignments - only through security groups

**Naming Convention:**

- `GC-PowerPlatform-[Department]-[Environment]-[Role]`
- Example: `GC-PowerPlatform-ISED-Prod-Makers`

**Security Score Impact:** Environment security groups contribute points for each environment configured.

### 2.2 Environment Security Roles (MANDATORY)

**Standard Role Assignments:**

- **System Administrator:** IT security personnel only (maximum 2-3 users per environment)
- **Environment Admin:** Designated environment managers
- **Environment Maker:** Authorized citizen developers
- **Basic User:** Read-only access for business users

**Custom Security Roles:** Create department-specific roles with minimal required permissions

**Security Score Note:** Environments with more than 10 administrators trigger a recommendation to reduce administrator privileges.

### 2.3 Managed Environments (MANDATORY for Production)

**Requirements:**

- Enable all production environments as Managed Environments
- Configure sharing limits and restrictions
- Enable data classification
- Implement solution checker enforcement
- Enable maker impact analysis

**Managed Environments Capabilities (2024-2025):**

| Capability | Category | Description |
|------------|----------|-------------|
| Environment Groups | Managed Governance | Group environments for consistent policy application |
| Weekly Admin Digest | Managed Governance | Automated reports on environment activity |
| Sharing Limits | Managed Governance | Control app sharing scope |
| IP Firewall | Managed Security | Network-layer access control |
| IP Cookie Binding | Managed Security | Enhanced session security |
| Customer Lockbox | Managed Security | Approve Microsoft support access requests |
| Customer-Managed Keys | Managed Security | Self-managed encryption (OPTIONAL) |
| Solution Checker Enforcement | Managed Operations | Quality gates for deployments |
| Pipelines | Managed Operations | Native ALM capabilities |

**Converting to Managed Environments:**

1. Navigate to Power Platform Admin Center > Security > Overview
2. View percentage of unmanaged environments
3. Select "Get started" to begin conversion
4. Select environments from Recommended or All eligible tabs
5. Accept terms and select "Turn on environment management"

### 2.4 Data Residency and Sovereignty (MANDATORY)

**Requirements:**

- All environments must be created in Canada Central or Canada East regions
- Enable data residency compliance
- Configure geographic data storage restrictions
- Implement cross-border data transfer controls

## NEW: 4. Power Platform Pipelines for ALM

### 4.1 Overview

Power Platform Pipelines provide native Application Lifecycle Management (ALM) capabilities that significantly reduce the effort required to implement healthy deployment processes. Pipelines are an official Microsoft Power Platform product feature that enables governed solution deployment.

**Benefits:**

- Admins configure automated deployment pipelines in minutes
- Makers have intuitive deployment experience without ALM expertise
- Centralized governance for citizen-led and pro-dev projects
- Solution prevalidation against target environments
- Automatic backup of all deployed solution versions
- Audit logs with who, what, when, where, and why (AI-assisted)

### 4.2 Pipeline Architecture

**Required Environments:**

| Environment Type | Purpose | Requirements |
|------------------|---------|--------------|
| Host Environment | Central management and configuration | Managed Environment with Dataverse |
| Development Environment | Solution creation and initial testing | Managed Environment with Dataverse |
| Target Environment(s) | UAT, Production deployment targets | Managed Environment with Dataverse |

**Pipeline Types:**

- **Platform Host:** Default tenant-wide host for maker self-service pipelines
- **Custom Host:** Admin-configured host for centralized governance

### 4.3 Pipeline Configuration (MANDATORY for Production Deployments)

**Setup Steps:**

1. Create dedicated host environment (or use platform host)
2. Install Power Platform Pipelines application in host
3. Associate development and target environments
4. Configure pipeline stages (Dev → UAT → Production)
5. Assign security roles (Deployment Pipeline Administrator, Deployment Pipeline User)
6. Configure approval workflows for production deployments

**Security Roles:**

| Role | Permissions |
|------|-------------|
| Deployment Pipeline Administrator | Full control over pipeline configurations |
| Deployment Pipeline User | Run pipelines on assigned environments |

### 4.4 Delegated Deployments (MANDATORY for Production)

**Requirement:** Enable delegated deployments to ensure least-privileged access.

**Configuration:**

- Makers submit deployment requests
- Admins or designated approvers review and approve
- Deployment executes with appropriate permissions
- No direct production access required for makers

**Benefits:**

- Secure production environments with approval-based deployments
- Makers don't need elevated permissions in target environments
- Full audit trail of all deployment requests and approvals

### 4.5 Pipeline Features for Governance

**Pre-Deployment Validation:**

- Missing dependencies detected before deployment
- Connection references validated
- Environment variables verified
- Solution checker enforcement (configurable severity levels)

**Post-Deployment:**

- Automatic solution backups
- Rollback capability to previous versions
- Deployment history with detailed audit logs

**Advanced Capabilities:**

- Multi-geo support for global deployments
- Cross-geo solution deployments (when enabled)
- Integration with Azure DevOps and GitHub for extensibility
- Service principal support for automated pipelines

### 4.6 Pipelines vs ALM Accelerator

| Aspect | Pipelines | ALM Accelerator |
|--------|-----------|-----------------|
| Complexity | Simple, native experience | Advanced, more configuration |
| Setup Time | Minutes | Hours to days |
| External Dependencies | None | Azure DevOps/GitHub required |
| Support | Official Microsoft product | Community-supported (CoE Kit) |
| Best For | Most organizations | Complex enterprise scenarios |

**Recommendation:** Start with Power Platform Pipelines and extend with ALM Accelerator only if advanced scenarios require it.

## 5. Data Protection and Privacy

### 5.1 Data Classification (MANDATORY)

**Requirements:**

- Implement Microsoft Purview data classification
- Label all Protected B data appropriately
- Configure automatic labeling policies
- Monitor data access and usage

### 5.2 Encryption (MANDATORY)

**Requirements:**

- Data encrypted at rest and in transit (Microsoft-managed by default)
- Customer-managed encryption keys (CMK) - **OPTIONAL** (see Section 5.3)
- Key rotation policies implemented (if using CMK)
- Encryption compliance monitoring

### 5.3 Customer-Managed Keys (CMK) - OPTIONAL

**Classification Change:** Customer-Managed Keys are now classified as **OPTIONAL** for PBMM compliance. Microsoft-managed encryption keys provide strong default encryption that meets security requirements.

**When to Consider CMK:**

- Regulatory requirements mandate customer-controlled encryption
- Organizational policy requires self-managed encryption keys
- Additional data protection control is required beyond Microsoft-managed keys
- Need to prevent Microsoft access to data by revoking key access

**CMK Overview:**

Customer-managed keys allow organizations to bring their own encryption keys from Azure Key Vault to encrypt Dataverse environment data. This provides:

- Self-managed database encryption key
- On-demand key rotation or swap capability
- Ability to revoke Microsoft access by revoking key permissions
- Migration path from legacy BYOK (Bring Your Own Key)

**Supported Services for CMK:**

- Dataverse (Custom solutions and Microsoft services)
- Power Automate (cloud flows)
- Power Apps (app source code and assets)
- Dynamics 365 applications (Sales, Customer Service, Field Service, etc.)
- Copilot Studio

**CMK Prerequisites:**

| Requirement | Details |
|-------------|---------|
| Azure Subscription | With Azure Key Vault or Managed HSM |
| Managed Environment | Required for CMK policy enforcement |
| Licensing | M365/O365 A5/E5/G5 or equivalent compliance SKU |
| Key Vault Configuration | Soft-delete and purge protection enabled |
| Key Type | RSA or RSA-HSM, 2048-bit or 3072-bit |

**CMK Implementation Steps (if implementing):**

1. Create Azure Key Vault with required security settings
2. Create RSA key in Key Vault
3. Create Power Platform Enterprise Policy
4. Grant Enterprise Policy access to Key Vault
5. Grant Power Platform admin read access to Enterprise Policy
6. Apply encryption to Dataverse environments
7. Document key management procedures

**Important CMK Considerations:**

- Environment is disabled during encryption process
- Key vault access is required for database restoration
- Do not delete keys for at least 28 days after rotation
- Locked environments (revoked key access) become inaccessible
- Default limit of 25 CMK-enabled environments per tenant

**CMK Security Score Impact:** Customer Lockbox (related feature) contributes to security score when enabled on Managed Environments.

### 5.4 Data Retention and Disposal (MANDATORY)

**Requirements:**

- Configure retention policies per government standards
- Implement secure deletion procedures
- Document data lifecycle management
- Legal hold capabilities

## NEW: 12. Center of Excellence (CoE) Starter Kit Integration

### 12.1 Overview

The Power Platform CoE Starter Kit is a reference implementation that demonstrates how to build sophisticated governance, monitoring, and adoption capabilities using Power Platform's native low-code tools.

**Important:** The CoE Starter Kit is a template/reference implementation, not a replacement for Managed Environments. Use Managed Environments for out-of-the-box governance and CoE Starter Kit for extended capabilities.

**Documentation:** [https://learn.microsoft.com/en-us/power-platform/guidance/coe/overview](https://learn.microsoft.com/en-us/power-platform/guidance/coe/overview)

**GitHub Repository:** [https://aka.ms/CoEStarterKitRepo](https://aka.ms/CoEStarterKitRepo)

### 12.2 CoE Starter Kit Components

| Component | Purpose | Relevance |
|-----------|---------|-----------|
| Core Components | Inventory sync, admin apps, Power BI dashboards | RECOMMENDED for visibility |
| Governance Components | Compliance processes, cleanup automation | RECOMMENDED for governance |
| Nurture Components | Maker community support, training | OPTIONAL for adoption |
| ALM Accelerator | Advanced DevOps integration | OPTIONAL for complex scenarios |

### 12.3 When to Use CoE Starter Kit

**Use CoE Starter Kit alongside Managed Environments when you need:**

- Extended inventory reporting beyond admin center
- Custom compliance workflows
- Maker community nurturing capabilities
- Integration with organizational data (departments, locations)
- Automated cleanup of orphaned resources
- Innovation backlog management

**Start with Managed Environments first for:**

- Environment creation controls
- Sharing limits
- IP firewall
- Weekly admin digest
- Solution checker enforcement
- Data policies

### 12.4 CoE Starter Kit Implementation Considerations

**Prerequisites:**

- Two production environments (test and production) for CoE deployment
- Service account or admin account for data collection
- Power BI workspace for dashboards
- Microsoft Entra security group for makers

**Data Collection Methods:**

1. **Cloud Flows (Traditional):** Uses Power Automate to collect inventory data
2. **Data Export to Azure Data Lake:** More efficient for large tenants (recommended for scale)

**Recommended Approach:**

1. Deploy Managed Environments for immediate governance benefits
2. Evaluate CoE Starter Kit Core Components for extended visibility
3. Implement Governance Components for automated compliance processes
4. Consider Nurture Components for maker community development

- [ ] Required licenses (M365 A5/E5/G5 or equivalent compliance SKU)

### A.4.2 Azure Key Vault Setup

**Key Vault Requirements:**

| Setting | Required Value | Purpose |
|---------|---------------|---------|
| Soft Delete | Enabled | Prevent accidental deletion |
| Purge Protection | Enabled | Mandatory retention period |
| Permission Model | Azure RBAC (recommended) | Role-based access control |
| Location | Canada Central/East | Data residency |

**Key Requirements:**

| Parameter | Value | Notes |
|-----------|-------|-------|
| Key Type | RSA or RSA-HSM | RSA-HSM for FIPS 140-2 Level 3 |
| Key Size | 2048 or 3072 bit | Minimum 2048-bit |
| Key Operations | Wrap, Unwrap | Required for encryption |
| Expiration | Set with monitoring | Configure alerts 90 days before |

### A.4.3 Enterprise Policy Creation

**PowerShell Example:**

```powershell
# Enterprise Policy ARM Template
$template = @{
    '$schema' = "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#"
    contentVersion = "1.0.0.0"
    resources = @(
        @{
            type = "Microsoft.PowerPlatform/enterprisePolicies"
            apiVersion = "2020-10-30"
            name = "GC-CMK-EntPolicy"
            location = "canada"
            kind = "Encryption"
            identity = @{
                type = "SystemAssigned"
            }
            properties = @{
                encryption = @{
                    state = "Enabled"
                    keyVault = @{
                        id = "/subscriptions/{sub-id}/resourceGroups/{rg}/providers/Microsoft.KeyVault/vaults/{vault-name}"
                        key = @{
                            name = "{key-name}"
                        }
                    }
                }
            }
        }
    )
}
```

### A.4.4 CMK Application Process

1. **Grant Enterprise Policy Permissions:**
   - Assign "Key Vault Crypto Service Encryption User" role to enterprise policy's managed identity

2. **Grant Admin Read Access:**
   - Assign "Reader" role to Power Platform administrators

3. **Apply to Environments:**
   - Navigate to Power Platform Admin Center > Security > Data and Privacy
   - Select Customer-managed encryption key
   - Select enterprise policy > Edit policy
   - Add environments > Save

**Important Notes:**

- Environment is disabled during encryption (duration depends on database size)
- Test in non-production environment first
- Document estimated downtime for production planning
- Maintain key access for minimum 28 days after rotation

### A.4.5 CMK Monitoring and Maintenance

**Regular Tasks:**

| Task | Frequency | Responsibility |
|------|-----------|----------------|
| Key access verification | Weekly | Key Vault Admin |
| Encryption status check | Weekly | Power Platform Admin |
| Key expiration monitoring | Monthly | Key Vault Admin |
| Key rotation | Per policy (e.g., annual) | Key Vault Admin |
| Access audit | Quarterly | Security Team |

## A.7 Compliance Verification Scripts

### A.7.1 PowerShell Compliance Check

```powershell
# Power Platform PBMM Compliance Verification Script
# Requires: Microsoft.PowerApps.Administration.PowerShell module

# Connect to Power Platform
Connect-PowerPlatformAdmin

# Verify Tenant Settings
$tenantSettings = Get-TenantSettings
$complianceResults = @{
    "EnvironmentCreationRestricted" = $tenantSettings.disableEnvironmentCreationByNonAdminUsers
    "TrialCreationRestricted" = $tenantSettings.disableTrialEnvironmentCreationByNonAdminUsers
    "ShareWithEveryoneDisabled" = $tenantSettings.powerPlatform.powerApps.disableShareWithEveryone
    "GuestCreationDisabled" = -not $tenantSettings.powerPlatform.powerApps.enableGuestsToMake
}

# Verify DLP Policies
$dlpPolicies = Get-AdminDlpPolicy
$tenantWidePolicyExists = ($dlpPolicies | Where-Object { $_.environments.count -eq 0 }).Count -gt 0
$complianceResults["TenantWideDLPPolicy"] = $tenantWidePolicyExists

# Verify Environment Security Groups
$environments = Get-AdminPowerAppEnvironment
foreach ($env in $environments) {
    $hasSecurityGroup = -not [string]::IsNullOrEmpty($env.SecurityGroupId)
    $isManagedEnv = $env.Properties.managedEnvironmentFeatures -ne $null
    Write-Output "Environment: $($env.DisplayName)"
    Write-Output "  Security Group: $hasSecurityGroup"
    Write-Output "  Managed Environment: $isManagedEnv"
}

# Output Compliance Summary
$complianceResults.GetEnumerator() | ForEach-Object {
    $status = if ($_.Value) { "COMPLIANT" } else { "NON-COMPLIANT" }
    Write-Output "$($_.Key): $status"
}
```
